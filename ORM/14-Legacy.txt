LATEST SEMANTIC CLARIFICATIONS
LATEST SEMANTIC CLARIFICATIONS — RAZ 14.04

This block captures the current operational semantics confirmed during runtime testing.
New clarifications are temporarily placed at the beginning of the ORM before later consolidation.

Core spatial hierarchy

Canonical hierarchy

parcour → room → object

Locus rule (mandatory)

• “locus” is not a DB hierarchy level
• “locus” is the spatial identity of any frame rendered in Godot

Interpretation

• In parcour: each frame = a locus station
• Entering a frame opens its room
• Inside room: frames remain locus-frames hosting object slots

Separation of concerns

• parcour / room / object = navigation + persistence layers
• locus = rendering identity (Godot only)

parcour
  → room
       → object

Definitions

parcour

• Represents the traversal layer of the system.
• Displayed as the main navigation space in Gatekeeper.
• The parcour contains the sequence of locus stations.
• PARCOUR_MAIN is the root entry for traversal.

room

• Represents the internal spatial layer opened from a parcour locus.
• A room is the navigable internal expansion of a locus station.
• The room contains object slots that must remain materially present and interactable.
• Entering a locus from the parcour opens its room.

object

• Represents an editable element or slot inside a locus room.
• Objects hold the working content (text, images, hints, etc).
• Objects do not open rooms.
• Objects are terminal nodes of the runtime spatial hierarchy.

Locus rule

• Every frame rendered by Godot is a locus in spatial terms.
• In parcour, the frame is a parcour locus station.
• In room, the internal frame remains a locus-frame oriented to object content.
• Therefore, “locus” remains the frame-level spatial identity, while “room” and “object” define the internal navigation and content layers.

Viewer navigation semantics

Enter Room
• Opens the room of the current locus.

Back to Parcour
• Returns to the parcour navigation space.

Show Objects
• Displays the objects contained in the current locus.

Go Parent
• Only appears when a valid parent entry exists.
• Must not appear for PARCOUR_MAIN.

Important rule

The term "corridor" is deprecated in operational semantics.
The correct runtime navigation layer is called "parcour".

Implementation rule

Gatekeeper navigation must reflect this hierarchy:

parcour → room → object

Objects remain editable entities inside locus rooms.

ENTRY TYPE SEMANTICS — CLEAN CONTRACT

Primary runtime semantic types:

locus
object

Deferred semantic layer:

parcour



locus

• Represents the main spatial station.
• A locus is the upper frame shown in the corridor.
• A locus opens a room.

object

• Objects hold working content.

  → may later produce a parcour asset layer for traversal

# Ajuste importante respecto al texto antiguo del ORM

Slot Runtime Compatibility Contract

The system must distinguish between canonical structural slots and transitional runtime compatibility placeholders.

Canonical rule:
- every canonical room-internal slot that is visible and interactable in runtime must correspond to a persisted structural row in `entries`
- canonical slot existence is not defined by row absence
- lifecycle of that persisted row is governed by `entryState`

Therefore:
- room/object structural slots must not use “missing row = canonical seed” as their main rule
- room/object structural slots may exist as persisted rows in `seed` or `active` state
- those slots remain materially present and interactable according to room-slot rules

Missing row

- missing row is not a seed state
- missing row is an invalid structural condition for canonical slots
- canonical slots must be backed by a persisted row in `entries`
- runtime may temporarily tolerate missing rows only as compatibility fallback

Transitional compatibility:
- runtime pseudo-keys such as `PARENTKEY__SLOT_##` may still exist as compatibility behavior in spawners
- this compatibility behavior is accepted only as migration/runtime support
- runtime pseudo-keys are not the preferred long-term definition of canonical slot existence

Corridor compatibility note:
- corridor rendering may still use runtime slot fallback behavior where legacy runtime compatibility requires it
- this does not redefine the canonical persistence rule for room/object structural slots

Important distinction:
- missing row
- runtime placeholder
- persisted seed row

must not be treated as equivalent states.

## 13. Slot contract

The system distinguishes three different concepts:

1. runtime placeholder
2. persistent seed row
3. active row

Definitions:

- runtime placeholder = visual fallback generated by Godot when a slot has no persisted row
- persistent seed row = structural row stored in `entries` to keep spatial stability
- active row = effective semantic row already promoted by the Builder

Structural integrity rule

The hierarchy assumes structural uniqueness of slots:

(parentKey, seq)

Recommended future protection:

UNIQUE(parentKey, seq)

This constraint is not yet enforced in all schemas
but reflects the intended structural model.

Structural identity:

- slot identity = (`parentKey`, `seq`)
- row identity = `KEY`

Resolved runtime identities:

- `slotKey` = stable runtime identity of the spatial slot used by Godot rendering
- `contentKey` = unique semantic knowledge identity assigned by Builder
- `navTargetKey` = explicit navigation destination resolved by Viewer / Gatekeeper
- `targetRealm` or `targetInterface` = optional future navigation context for warp and cross-realm jumps

Rules:

- a slot may exist visually without semantic content
- a slot may also exist as a persisted seed row
- the slot renderer must bind to stable slot identity first
- semantic knowledge must not be identified only by the visual slot
- navigation must not depend directly on slot naming alone
- warp navigation must resolve through `navTargetKey`, not by altering structural hierarchy
- when a persisted seed is promoted, slot identity remains stable
- promotion changes lifecycle state, not spatial identity


Navigation resolution contract

The system distinguishes three separate planes:

1. spatial plane
2. semantic plane
3. navigation plane

Spatial plane:
- defines where the slot exists
- governed by (`parentKey`, `seq`) and stable `slotKey`

Semantic plane:
- defines what knowledge is assigned to the slot
- governed by `contentKey`

Navigation plane:
- defines where the user goes when activating the slot
- governed by `navTargetKey`
- may remain local by default
- may later resolve a warp destination or cross-realm interface without rewriting slot structure

Default rule:

- no warp: `navTargetKey` resolves to local assigned content
- warp: `navTargetKey` may resolve to another locus, entry, realm, or interface target

This separation is mandatory so warp does not corrupt slot structure or semantic identity.



State model

Recommended lifecycle field:

- `entryState = 'seed' | 'active'`

Current compatibility note:

If the active schema does not yet include `entryState`, older runtimes
may represent seed compatibility using values such as:

- `layer = 'seed'`
- `entryType = 'seed'`

Those compatibility markers should be treated as transitional behavior.
The preferred long-term contract is an explicit lifecycle field
separate from semantic type.



Semantic rules:

- `seed` rows are structural, not effective knowledge data
- `seed` rows must stay hidden from semantic views, exports, and content listings
- the bridge must not open or promote seeds by accident
- only active rows participate as effective entries in semantic workflows

Authority rules:

- Godot may render runtime placeholders and read persisted seeds
- Godot may support structural stability of the visual runtime
- the Builder controls promotion from `seed` to `active`

Seed activation rule:

A persisted seed becomes an effective entry only when the Builder
promotes its lifecycle state.

parentKey
seq

Seed promotion must not change slot identity.

Promotion updates the row from structural placeholder state to

entryState is a target schema field and may not yet exist

## 12. Bootstrap de runtime y materialización de entries

Contrato actualizado

The system startup no longer grants Godot any SQLite bootstrap authority.

Separación de responsabilidades:

Godot = persistent 3D runtime surface + bridge reader
RAZ12 = canonical SQLite writer and semantic authority

### Persistent 3D runtime surface

Godot must guarantee that the 3D interaction surface remains materially available at runtime.

Allowed Godot responsibility:

• keep corridor and room slot surfaces materially present for interaction
• keep every spatial slot operational even when no effective row is available
• read SQLite slot lifecycle state (`seed` / `active`)
• render placeholder state for `seed`
• render effective interactive state for `active`
• write bridge coordination files
• preserve stable 3D interaction even when content changes in SQLite

Restriction:

• Godot does not create SQLite rows
• Godot does not update SQLite rows
• Godot does not perform semantic editing
• Godot does not own lifecycle transitions
• Godot reflects lifecycle transitions written by RAZ12

### Canonical SQLite authority

RAZ12 remains responsible for:

• creating effective rows
• creating persisted seed rows when structural persistence is required
• editing content (`body_text`)
• managing `seq`
• managing `assets`
• performing lifecycle transitions `seed -> active`
• performing lifecycle transitions `active -> seed`
• all semantic operations in SQLite

Bridge behavior

`open_key.txt` remains the canonical bridge signal emitted by Godot selection.

Current accepted runtime behavior:

• if `open_key.txt` contains an existing KEY, RAZ12 opens that existing row
• if `open_key.txt` contains a valid structural slot key of the form `PARENTKEY__SLOT_##` and that exact row does not yet exist, RAZ12 may materialize that exact slot row in SQLite
• Godot does not create rows; Godot only emits the runtime key through bridge
• row validation and row materialization remain Builder / RAZ12 responsibilities

Required preserved values at materialization:

• `key` = exact slot key received from bridge
• `parentKey` = derived parent key
• `seq` = derived slot sequence

Recommended lifecycle after materialization:

• `entryState = 'seed'`

Compatibility markers such as `entryType = 'seed'` and `layer = 'seed'` may still exist temporarily if required by the active schema.

Important distinction:

• Godot emits intent
• RAZ12 validates and materializes
• SQLite stores the resulting row
• Godot renders the refreshed state

### Slot and row separation
The ORM distinguishes spatial slot identity from persisted row identity.
* slot identity = (parentKey, seq) or stable runtime slotKey
* row identity = immutable KEY
A spatial slot is always preserved by Godot as part of the parcour structure.
Row lifecycle is independent from slot existence.
Deleting or demoting a row never removes the slot itself.
Promotion or demotion changes row lifecycle, not slot existence.

### Seeds and activation contract
Row state defines rendering behavior, not spatial existence.
* active → Godot renders the slot as real content
* seed → Godot keeps the slot spatially available but does not render it as active content
Changing active ↔ seed modifies state only and never removes the slot.

The system may persist structural placeholder rows in `entries`
to keep corridor, room, and frame initialization stable.

A seed is not effective semantic data.
A seed is a declared structural placeholder that occupies a valid slot
until the Builder promotes it to active state.

Recommended fields:

* `entryType` = structural kind (`parcour`, `locus`, `object`)
* `entryState` = lifecycle state (`seed`, `active`)

Structural rules:

* `KEY` remains the immutable identity of the row
* `(parentKey, seq)` remains the structural identity of the slot
* a seed may persist in SQLite without being treated as effective knowledge data
* seed rows must be hidden from semantic data views, exports, and content listings
* promotion from seed to active does not create a new KEY or a new slot

Promotion rule:

* the Builder may promote:
  `entryState: seed -> active`

At promotion time, the row keeps the same:

* `KEY`
* `parentKey`
* `seq`

and receives its effective semantic role through `entryType`
such as `locus` or `object`.

This contract allows runtime stability without polluting semantic data.

Deletion rule

Builder delete is now defined operationally as `clean`.

`clean` does not remove the persisted row.
`clean` does not change `KEY`.
`clean` does not change `parentKey`.
`clean` does not change `seq`.

`clean` preserves structural slot identity and row identity while removing effective payload.

Builder must only:

• clear effective payload as required
• delete asset rows associated with the same `KEY`
• delete physical assets associated with the same `KEY`
• change lifecycle state from `active` to `seed`

Recommended placeholder state after clean:

• neutral placeholder title such as `Seed XX`
• empty or placeholder `body_text`
• same persisted row
• same persisted `KEY`
• same structural slot `(parentKey, seq)`

Godot must then read that state and re-render the same 3D slot as structural placeholder.

The spatial interaction surface must remain available at all times.

 **Runtime Architecture Addendum — RAZ13.0 Gatekeeper Integration**:

Se estableció un **runtime físico único** para Alexandria basado en carpeta `data`. La estructura congelada es:

`C:\Alexandria\data`
`alexandria.db`
`assets\`
`bridge\`

Las rutas quedan centralizadas en `AlexandriaPaths.cs`, que expone `GetRoot()`, `GetDbPath()`, `GetAssetsRoot()` y `GetBridgeRoot()`. La lógica histórica con `%APPDATA%` se considera solo fallback técnico, no contrato arquitectónico.

Se fijó la **separación de procesos** entre editor y mundo 3D.
`RAZ12 (Builder)` es la **autoridad absoluta de escritura** sobre SQLite y generación de assets.
`Godot Gatekeeper` es **solo lector de SQLite** y escritor de archivos auxiliares del bridge. Godot no puede modificar SQLite para ningún propósito.

La comunicación entre procesos se define mediante **filesystem bridge**. El conjunto mínimo de archivos del protocolo es:

`bridge/open_key.txt`
`bridge/return_frame_key.txt`
`bridge/refresh_now.txt`

Existe adicionalmente `active_key.txt`, utilizado por el viewer como señal auxiliar, pero no forma parte del loop mínimo obligatorio.

Se introdujo el sistema de **pseudo-slots runtime** para mantener grillas fijas sin colisiones de identidad. Los slots vacíos generan keys temporales con formato:

`PARCOUR_MAIN__SLOT_01`
`PARCOUR_MAIN__SLOT_02`

Estas pseudo-keys son generadas por spawners en runtime y **nunca deben persistirse en SQLite**.

`Frame01` aplica bloqueo de navegación sobre pseudo-slots verificando la presencia de `__SLOT_` en la key. Los slots vacíos no abren viewer, no escriben `open_key.txt` y no generan navegación.

Se implementó un **launcher automático del Builder** desde Godot para garantizar que el backend esté activo cuando se intenta abrir un entry. Si el proceso no está corriendo, se ejecuta `launch_raz12.ps1`.

El corredor del palace se genera dinámicamente mediante `CorridorSpawner`, que consulta SQLite por hijos de `PARCOUR_MAIN`, clona el template `Frame01`, asigna `locus_key` y calcula spacing dinámico mediante `ComputeFrameGap()` basado en el contenido visual del locus.

ViewerMin functions as a lightweight viewer and navigator capable of parent traversal, child listing and locus entry. Este visor lee `body_text` en formato JSON desde SQLite, renderiza bloques de texto e imágenes, y permite navegación jerárquica básica.

Para preservar continuidad espacial, se implementó un sistema de **respawn al salir de locus**. Al abandonar un room, se escribe `return_frame_key.txt`; `World` busca el frame correspondiente y reposiciona la cámara en esa ubicación.

El mundo mantiene además un **watcher de refresh** sobre `refresh_now.txt`, que permite reconstruir el corredor en caliente cuando el Builder modifica la base de datos.

La carga de imagen principal de cada frame sigue una estrategia jerárquica: primero intenta localizar un asset con `role='hero'` en SQLite; si no existe, utiliza `assets/{KEY}/cover.png`.

La escena base `World.tscn` contiene `CameraRig`, `Frames`, `Corridor`, `WallPath` y el template `Frame01`, que es duplicado dinámicamente por el spawner.

De esta fase emergen cuatro decisiones estructurales del sistema:

1. runtime físico único `C:\Alexandria\data`
2. SQLite escrita exclusivamente por RAZ/Builder
3. comunicación entre procesos solo mediante filesystem bridge
4. slots vacíos representados mediante pseudo-keys runtime

Estas reglas forman parte del **contrato arquitectónico del ORM** porque definen la integridad del sistema aunque no modifiquen el schema SQL.

**Aporte de 13.2 al ORM de Alexandria**

13.2 consolidó el paso de un modelo parcialmente conceptual a un modelo operativo centrado en una sola tabla principal: `entries`. El estado efectivo de `entries` quedó como `key TEXT PRIMARY KEY`, `createdAt TEXT`, `updatedAt TEXT`, `title TEXT`, `layer TEXT`, `parentKey TEXT`, `seq INTEGER`, `body_text TEXT`, `entryType TEXT`, `capacity INTEGER`, `version INTEGER NOT NULL DEFAULT 1`. La lógica real del sistema ya no gira alrededor de una tabla de relaciones para navegación cotidiana, sino alrededor de la combinación `parentKey + seq`, que define jerarquía y slot físico dentro del parent.

13.2 también consolidó `assets` como tabla auxiliar de archivos con `assetKey TEXT PRIMARY KEY`, `entryKey TEXT NOT NULL`, `fileName TEXT NOT NULL`, `mime TEXT NOT NULL DEFAULT ''`, `role TEXT NOT NULL DEFAULT ''`, `createdAt TEXT NOT NULL`, más índice por `entryKey`. La lógica jerárquica quedó así: `PARCOUR_MAIN` es el root único con `parentKey = NULL`; todos los demás entries deben tener `parentKey`. `entryType` pasó a ser la semántica real del sistema con valores `parcour`, `locus` y `object`, mientras `layer` quedó redundante y debe tratarse como legado a retirar después. `capacity` no se impone en SQL; se aplica solo desde la lógica de aplicación, y su alcance real en 13.2 es `parcour -> loci` y `locus -> objects`.

13.2 fijó también el cambio más importante para Viewer/Godot: los slots vacíos no viven como rows reales, sino como placeholders virtuales reconstruidos por runtime mediante pseudo-keys del tipo `CurrentParentKey__SLOT_XX`. Eso eliminó la ambigüedad anterior donde slots vacíos compartían identidad del parent. En paralelo, `body_text` dejó de ser texto simple y pasó a operar como JSON blocks, con soporte operativo real para bloques `p` e `img`, donde las imágenes se enlazan por `assetKey`.

Otra contribución de 13.2 fue aclarar dependencias reales del runtime: Godot y Viewer ya dependen explícitamente de `parentKey`, `seq`, `entryType`, `body_text` y `assets`; no de `relations`. La deuda técnica que 13.2 deja claramente identificada para congelar el ORM es agregar un índice único parcial sobre slots, idealmente `UNIQUE(parentKey, seq) WHERE parentKey IS NOT NULL`, para blindar en SQL lo que hoy solo protege la lógica.

**Addendum — Runtime Contract and Viewer Loop (RAZ 13.2)**

Durante 13.2 se fijaron reglas operativas que conectan el ORM con el runtime visual sin modificar el esquema de datos.

Se consolidó la **separación de responsabilidades del sistema**. El Builder (Flutter / RAZ12) es la única autoridad de datos y el único componente que escribe en SQLite. Godot Gatekeeper (RAZ13) actúa únicamente como renderizador y navegador. Godot puede leer `alexandria.db`, pero no modificarla.

Se estableció el **contrato de runtime filesystem-first**. El sistema funciona alrededor de un root operativo único con tres elementos: base de datos, assets y bridge. La estructura establecida es `AlexandriaRoot/alexandria.db`, `AlexandriaRoot/assets/{KEY}/` y `AlexandriaRoot/bridge/open_key.txt`. Se introdujo **AlexandriaPaths** como punto único de resolución de rutas. Este componente centraliza `GetDbPath`, `GetAssetsRoot` y `GetBridgeRoot`, eliminando rutas hardcodeadas y permitiendo portabilidad del runtime.

Se estableció el **sistema de assets portable**. Los archivos binarios no viven en SQLite; se almacenan en filesystem bajo `assets/{KEY}/`. El contenido textual en `body_text` referencia los assets mediante `assetKey`.

**Addendum — Architectural Transition to Hierarchical Navigation (RAZ 13.3)**

Durante esta fase se produjo el cambio estructural más importante del sistema: el paso de un almacenamiento plano de entries a un **modelo jerárquico navegable basado en `parentKey + seq` con navegación persistente por `activeKey`**.

Este cambio consolidó el ORM como un sistema capaz de representar estructuras de conocimiento recorribles, no solo registros aislados.

La lógica central quedó distribuida en varios componentes del runtime WinForms original:

`EntriesDao` estableció la creación jerárquica. Se introdujeron funciones como `CreateParcour`, `CreateLocus`, `CreateInternal` y `GetNextSeq`, que generan nuevos entries respetando el contrato `parentKey + seq`. También se incorporó `SetEntryId`, permitiendo formar identificadores legibles y ordenables.

`SQLiteInit` añadió las migraciones idempotentes necesarias para soportar jerarquía real sin romper bases anteriores. En particular se introdujeron las columnas `parentKey` y `seq` en `entries`, habilitando la navegación estructurada.

`NavEngine` se convirtió en el motor de navegación persistente. Este componente introdujo el concepto de `ActiveKey` como estado global de navegación y permitió operaciones como `GoTo`, `GoParent`, `ChildrenKeys` y `GoFirstChild`. Con esto el sistema dejó de depender de listas estáticas y pasó a operar como un árbol navegable con estado.

`RelationsDao` y `ChildrenPicker` resolvieron el orden visible de los hijos. `ChildrenPicker.LoadSortedChildren` obtenía los hijos y los ordenaba utilizando el prefijo numérico del `entry_id`, haciendo que la jerarquía fuera legible para el usuario y no dependiera del orden arbitrario de inserción.

La interfaz principal quedó estabilizada mediante la pantalla compuesta `GatekeeperView + ViewerView`. En `GatekeeperView` se consolidó el comportamiento de navegación separando claramente **preview** y **apertura real**: `SelectedIndexChanged` activa preview del entry seleccionado, mientras `DoubleClick` ejecuta la apertura. Este patrón fijó una navegación clara entre exploración y edición.

El editor también adoptó una decisión arquitectónica relevante: el Builder dejó de almacenar RTF o binarios incrustados en la base de datos. En `ViewerBuilderForm.SaveNow()` se guardó únicamente texto plano (`_rtb.Text`). Esto preserva la base SQLite como almacenamiento estructurado y evita contaminación con blobs de formato.

**Resultado arquitectónico de esta iteración**

El sistema dejó de ser un repositorio plano y se transformó en un **grafo jerárquico navegable**, donde:

* `entries` contiene los nodos del sistema
* `parentKey + seq` define la posición jerárquica
* `entry_id` aporta legibilidad y orden visual
* `activeKey` mantiene el estado de navegación
* la UI navega el árbol en lugar de listar registros

Este modelo sentó las bases para las implementaciones posteriores del viewer Godot, que reutiliza el mismo contrato jerárquico (`parentKey + seq`) para reconstruir visualmente el corredor y los loci.

## RAZ 13.3 — Frozen rules

**Bootstrap of the parcour**

Initial child counts used during early runtime setup are compatibility behavior,

# Alexandria — Iteration 13.6

Operation Reference Manual Consolidation

## Architectural State

The Alexandria system now operates with a clear separation between semantic authority and spatial reader.

The **Builder layer (RAZ12 / Flutter)** is the semantic authority. It owns the database schema, content structure, child creation, migrations, and asset indexing.

The **Gatekeeper layer (Godot)** is a spatial reader. It renders corridor navigation, loads entry content, and interacts with the Builder through the bridge mechanism.

The interaction model is therefore:

Builder → creates and manages semantic structure
Gatekeeper → reads and visualizes structure

Gatekeeper may perform limited structural bootstrap
for runtime stabilization (for example seed rows),
but must not create or modify effective semantic entries.

This separation resolved earlier ambiguity about which subsystem controls hierarchy and persistence.



# Data Model

## entries table

The active schema includes:

key
title
layer
parentKey
seq
body_text
entryType
capacity
version


entryType defines the semantic role of the entry:

parcour → corridor root (traversal layer)
object  → editable internal child (room content)
seed    → structural placeholder

locus clarification

• “locus” is not a persistence entryType
• “locus” defines the spatial identity of any frame rendered in Godot
• A frame can represent:
  - a parcour station
  - an internal room slot (object host)


layer remains present for compatibility with earlier runtimes.


Hierarchy is explicitly defined by:

parentKey
seq

Structural slot identity:

(parentKey, seq)

The database should eventually enforce:

UNIQUE(parentKey, seq)

to prevent slot duplication.



This replaces the older navigation model that relied primarily on relations.

## assets table

Assets represent binary resources stored outside the database.

Binary files must never be stored inside SQLite rows.
SQLite stores references only.

Each asset is associated with an entryKey and identified by assetKey.

Files are stored physically in the Alexandria assets root.



# Content Model

Content of an entry is stored in **body_text** as JSON blocks.

Two block types are active:

p → paragraph text
img → image reference using assetKey

Images are resolved through the combination:

active entryKey
assetKey inside body_text



# Asset Roles

Assets follow a semantic role classification:

hero → cover image of a frame or locus
parcour → corridor visual panels / path segments
img → internal content image referenced by body_text

This rule aligns Builder semantics and Godot rendering behavior.



# Hierarchy Rules

Hierarchy is defined through:

parentKey + seq

Slot identity:
(parentKey, seq)

Entry identity:
KEY

KEY does not define structural position.

Ordering and spatial placement are defined exclusively by:

(parentKey, seq)

This structure governs corridor layout, room navigation, and child ordering.

relations do not define structural hierarchy.

relations are reserved for transversal graph features such as warp navigation.



# Bootstrap Structure

The Builder runtime seeds a default root structure.

PARCOUR_MAIN is created as the root entry.

Initial corridor slots may be created beneath PARCOUR_MAIN
as structural placeholders.

The number of slots is a runtime configuration detail and
is not part of the ORM contract.

Slots are identified structurally by:

(parentKey, seq)

A slot may contain either:

seed   → structural placeholder
active → effective semantic entry

Promotion from seed to active does not change:

KEY
parentKey
seq

This establishes the initial corridor structure used by the Gatekeeper.



# Child Creation Logic

createChildEntry() implements semantic cloning.

The cloning process now follows three required steps:

1. Copy the physical asset file
2. Insert a new row in the assets table
3. Rewrite assetKey references in body_text

Only images actually used by the child body are cloned.

The process:

• decode parent body blocks
• collect used image keys
• filter parent assets
• copy relevant files
• create assetKeyMap
• rewrite img blocks in child body_text

This ensures images resolve correctly when the child entry is viewed.



# Capacity Enforcement

Each entry may define a capacity value limiting the number of children.

createChildEntry() validates current child count against capacity before inserting a new entry.

However this validation currently exists only in the helper path and not in every creation path (for example bridge bootstrap).

hotkeys for editing actions

Currently the operational behavior still clones the full parent body unless a caller explicitly provides selected blocks.

Godot operates primarily as a spatial reader of Builder data, but the current 14.04 runtime includes limited bootstrap writes to SQLite for stabilization paths such as seed creation.

La herencia por defecto de contenido queda así:

* si `sourceBlocks == null` → el child hereda todo el `body_text` del parent
* si además el parent está vacío → se usa párrafo vacío base

`ViewerMin` queda como puerta práctica de navegación:

* `corridor -> locus`
* `locus -> room`

`Frame01` abre `ViewerMin`; `ViewerMin` ejecuta `Enter Locus`.

`LocusRoom` se construye leyendo hijos por:

`parentKey = locusKey`
`seq`

igual que el corridor, pero usando `LocusSpawner`.

Los placeholders `__SLOT_xx` son solo runtime. No deben persistirse en SQLite.

`CurrentParentKey` pasa a gobernar qué estructura renderiza Godot. El corridor o room visible depende de ese parent activo.

`entryType` operativo en Builder queda confirmado con tres niveles:

* `parcour`
* `locus`
* `object`

`object` no genera room. `ViewerMin` bloquea `Enter Locus` sobre `object`.

`recompactChildren()` queda como mecanismo canónico de Builder para cerrar huecos de `seq`. Godot solo consume `seq`.

Godot mantiene acceso **read-only** sobre SQLite. La escritura operativa sigue yendo al bridge/filesystem, no a la DB.

La semántica activa de assets y bloques queda así:

* `hero` = portada / cover visual del frame
* `parcour` = paneles / camino visual
* `img` = bloque de imagen dentro de `body_text`

Si faltan objects reales, `LocusSpawner` rellena slots con placeholders visuales igual que el corridor.

`open_key.txt` queda confirmado como bridge escrito por Godot para que Builder abra el entry.

`return_frame_key.txt` queda confirmado para volver al frame de origen.

`refresh_now.txt` no queda sellado en este cierre porque no se revalidó aquí el watcher exacto en `World.cs`.

`capacity` está efectivamente aplicada en `createChildEntry()`, pero no queda cerrada todavía como enforcement universal en todos los caminos de creación.

La intención contractual de `deleteChildEntry()` es restringir delete a nivel `object` y no permitir borrar loci del parcour por hotkey, pero eso todavía no debe presentarse como enforcement final; queda como pendiente congelado.

# RAZ 13.8 — Confirmaciones adicionales

**Q1. ¿Qué ocurre con `open_key.txt` después de ser consumido por el Builder?**
A1. El Builder lo elimina inmediatamente después de leerlo. `_handleBridgeOpenKey()` lee el archivo y ejecuta `deleteSync()` para evitar reaperturas repetidas.



**Q2. ¿Quién escribe `active_key.txt`?**
A2. Godot lo escribe desde `ViewerMin.SaveActiveKey()`. Este archivo representa el entry actualmente activo en el Gatekeeper.



**Q3. ¿Qué ocurre cuando el Builder recibe un key que no existe en SQLite?**
A3. El runtime crea automáticamente un entry nuevo bajo `parentKey = PARCOUR_MAIN` y lo trata como un locus dentro del parcour.



**Q4. ¿El corridor genera frames según el número de children en DB?**
A4. No. `CorridorSpawner` genera una cantidad fija de frames definida por `TotalFrames`. Los children reales solo ocupan slots disponibles.



**Q5. ¿El room de un locus genera slots según los objects existentes?**
A5. No. `LocusSpawner` usa una cantidad fija de slots (por ejemplo 20) y luego asigna objects reales si existen.



**Q6. ¿Puede modificarse estructuralmente el nodo `Frame01`?**
A6. No. `Frame01` es el template base utilizado por los spawners para duplicar frames en runtime. Alterarlo rompe la generación dinámica de frames.



**Q7. ¿Cómo se renderizan los placeholders `PARENT__SLOT_XX`?**
A7. Se renderizan como frames vacíos sin hero ni assets. Representan slots visuales sin contenido real.



**Q8. ¿Cómo detecta el Builder eventos del bridge (`open_key.txt`)?**
A8. Mediante polling con `Timer` (~350 ms). El runtime revisa periódicamente la existencia del archivo.



**Q9. ¿Se crea automáticamente la carpeta `assets/{entryKey}` al crear un entry?**
A9. No. La carpeta se crea únicamente cuando se guarda el primer asset asociado al entry.



**Q10. ¿Qué ocurre si `C:\Alexandria\data` no existe?**
A10. El runtime crea automáticamente el directorio. Ese path es el root operativo del sistema.



**Q11. ¿De dónde reconstruye contenido `ViewerMin`?**
A11. Desde tres fuentes:

SQLite entries.body_text
tabla assets
filesystem assets/{entryKey}

El bridge no participa en la reconstrucción de contenido.



**Q12. ¿Cómo funciona el refresh visual en Godot?**
A12. El refresh reconstruye el contenido dentro de la misma escena llamando a `ShowKey()` y regenerando los bloques visuales. No se recarga la escena completa.



**Q13. ¿Las claves `PARENT__SLOT_XX` pueden entrar en SQLite o en el bridge?**
A13. No. Son claves temporales generadas por los spawners para slots visuales y nunca deben persistirse en DB ni en archivos bridge.

RAZ 13.9 — Confirmaciones adicionales

Q1 — ¿El bridge puede crear entries automáticamente?
Sí. Cuando aparece `open_key.txt`, el runtime Flutter busca el key en `entries`. Si no existe, inserta un nuevo entry como `locus` bajo `PARCOUR_MAIN` con `seq = nextSeq`. Este comportamiento está implementado en `main.dart`, por lo que en 13.9 la autocreación de loci por bridge es comportamiento real del sistema.

Q2 — ¿Dónde vive realmente la capacidad (`capacity`)?
Es mixta. En Builder/Flutter el valor vive en `entries.capacity` y se consulta en `createChildEntry()` para validar creación de hijos. Sin embargo, en Godot los spawners siguen teniendo límites fijos (`TotalFrames = 10` para corridor y `TotalSlots = 20` para locus). En 13.9 el contrato es: `capacity` vive en DB para la semántica del Builder, pero Godot aún usa topes hardcoded para spawn visual.

Q3 — ¿Cómo carga Frame01 los assets?
Frame01 resuelve assets por sí mismo usando `locus_key`. `_load_cover()` llama a `ResolveHeroPath()`, consulta SQLite buscando `role='hero'` y construye la ruta usando `AlexandriaPaths.GetAssetsRoot()`. Si no existe hero, cae a `assets/{KEY}/cover.png`. No recibe rutas desde los spawners.

Q4 — ¿Las rutas de assets ya están completamente unificadas?
No totalmente. Frame01 ya usa `AlexandriaPaths.GetAssetsRoot()` y `GetDbPath()`. Sin embargo, algunos spawners todavía conservan rutas heredadas o referencias hardcoded (por ejemplo launchers de desarrollo). En 13.9 la migración hacia `AlexandriaPaths` está iniciada pero aún no completa.

Q5 — ¿`refresh_now.txt` forma parte del contrato del bridge?
Existe y funciona. `World.cs` ejecuta un watcher que revisa `refresh_now.txt`, llama `CorridorSpawner.RefreshFromDb("PARCOUR_MAIN")` y elimina el archivo. Sin embargo, en 13.9 debe considerarse mecanismo operativo de refresh, no contrato semántico central del modelo.

2. Lógica del sistema que quedó confirmada

La identidad estructural moderna del sistema se rige por parentKey + seq. Ese par define el slot físico, el orden de hermanos y la reconstrucción del corridor o del room. Tanto CorridorSpawner como LocusSpawner consultan SQLite por parentKey y seq, y cuando no existe row generan un pseudo-slot temporal parent__SLOT_## solo para runtime. Esto confirma que el viewer ya no infiere jerarquía desde relations, sino desde entries.

Los slots vacíos no son conocimiento real. Son placeholders de runtime generados en spawners, bloqueados por Frame01, y nunca deben comportarse como entries. Este aislamiento por pseudo-key fue un hallazgo importante porque elimina colisiones de identidad y explica por qué corridor y room pueden seguir mostrando capacidad espacial fija sin contaminar SQLite.

El bridge no es replicación ni sincronización de estado completo. Es un event bus mínimo por filesystem. Los archivos activos que aparecen en el flujo actual son open_key.txt, return_frame_key.txt, refresh_now.txt y active_key.txt. Cada uno representa una intención puntual: abrir, volver al frame, refrescar, o exponer la key activa. No existe contrato de “sincronizar mundo y builder”; existe contrato de “emitir señales mínimas”.

assets.role dejó de ser metadata pasiva. hero ya gobierna la portada del frame en Godot, y parcour ya gobierna spacing y paneles del corridor. Esto vuelve a role una capa semántica de render, no solo un campo descriptivo. También alinea con el contrato legado donde assets del parcour son geográficos y blocks IMG del locus son pedagógicos.

ViewerMin ya no cabe en la definición de “viewer mínimo” estrictamente pasivo. El código real lo posiciona como un viewer+navigator ligero, porque conoce parent, children, enter locus y back to parcour. Este comportamiento debe quedar congelado en ORM para evitar que más adelante se documente como si siguiera siendo solo una vista de lectura.

Initial seeding contract

A missing row, a runtime placeholder, and a persisted seed row are not
the same thing.

The preferred ORM model is:
Missing row

- missing row is not a seed state
- missing row is an invalid structural condition for canonical slots
- canonical slots must be backed by a persisted row in `entries`
- runtime may temporarily tolerate missing rows only as compatibility fallback

- missing row = no persisted structure for that slot
- runtime placeholder = visual fallback only
- persisted seed row = structural placeholder stored in SQLite
- active row = effective semantic entry

Older bootstrap behavior from previous runtimes should be treated as
historical compatibility, not as a contradictory contract.

🧠 IDEAS FUERA DE LA HOJA DE RUTA (pero coherentes)

1. Ecos de navegación (ghost traces)

· Cuando recorres un Parcour, que queden "rastros tenues" de tu paso anterior: marcas de qué loci visitaste, cuánto tiempo estuviste, qué objetos abriste.
· No es historial textual, es visualización espacial de tu propia navegación.
· Útil para: ver patrones de estudio, notar qué ignoras, recuperar caminos mentales previos.

2. Capas de atención (focus layers)

· Un Locus puede tener múltiples "capas" de información que se revelan según tu nivel de atención o tiempo invertido.
· Capa 1: cover + hint (siempre visible)
· Capa 2: al detenerte +2 segundos, aparece un resumen o imagen secundaria
· Capa 3: al hacer foco explícito (clic), se abre el contenido completo
· Diseño: la interfaz reacciona a tu atención, no solo a clics.

3. Paisajes de repaso (review landscapes)

· Cuando entras en modo "review", el corredor se transforma: los loci pendientes se iluminan, los dominados se atenúan, los difíciles cambian de color.
· No es una pantalla de estudio aparte: el espacio mismo se convierte en interfaz de repaso.

4. Sombras de relaciones (relation shadows)

· Cuando un Locus tiene Warps, proyecta una "sombra tenue" hacia esos destinos, visible solo si te acercas o si activas "modo exploración".
· Las relaciones se sienten como presencias invisibles en el espacio, no como líneas en un gráfico.

5. Objetos encontrados (drift items)

· A veces, al navegar, podrías encontrar "objetos" que no pertenecen a ningún Locus: son notas sueltas, fragmentos Raw que flotan temporalmente.
· Diseño: aparecen como destellos, puedes recogerlos y luego decidir si los incorporas a un Locus o los dejas ir.
· Juega con la metáfora de "basura cognitiva" que puede volverse tesoro.

6. Puentes de contexto (context bridges)

· Al teletransportarte de un Locus a otro vía Warp, el sistema podría mostrar un "puente" visual: una transición donde ves ambos loci simultáneamente, con un indicador de por qué están relacionados.
· Refuerza la conexión semántica antes de llegar al destino.

7. Memoria del espacio (space memory)

· Si vuelves a un Parcour después de días, el espacio podría mostrar tenuemente dónde estuviste más tiempo, qué abriste, qué ignoraste.
· No como estadísticas, sino como cambios sutiles en la iluminación o textura.

8. Ritmos de estudio (study rhythms)

· El corredor podría cambiar su comportamiento según la hora del día o tu patrón de uso:
  · Por la mañana: colores más fríos, ritmo rápido
  · Por la noche: tonos cálidos, transiciones suaves
· También podría sugerir "pausas" si llevas mucho tiempo sin repaso.

9. Diarios de navegación visuales (navigation diaries)

· Al final de una sesión, el sistema podría ofrecerte un "mapa mental" de tu recorrido: una visualización abstracta de qué loci tocaste, qué warps usaste, dónde pasaste más tiempo.
· No es un log de texto, es una huella visual que puedes guardar o compartir.

10. Capas de intención (intention layers)

· Antes de entrar a un Parcour, podrías elegir una "intención": explorar, repasar, buscar, crear.
· El espacio se reorganiza levemente según la intención: los loci relevantes se acercan, los irrelevantes se alejan o atenúan.

Un Parcour no es una lista fija de Loci. Es un conjunto de relaciones SON que pueden ser filtradas, ordenadas y presentadas según la intención actual del usuario.

4. Algoritmo de generación del Pasillo

Dado:

· parcourKey (actual)
· intent (explore/review/seek/drift)
· Opcional: filter (texto, tags)

Paso 1: Obtener hijos SON base


sql
SELECT r.childKey, r.ord, e.*
FROM relations r
JOIN entries e ON r.childKey = e.key
WHERE r.parentKey = ? AND r.relType = 'SON'
ORDER BY r.ord ASC;


Paso 2: Aplicar filtro según intent (en memoria o SQL)

Intent Filtro
Explore Ninguno (todos)
Review e.reviewDue < ahora O e.lastVisit < limite
Seek e.title LIKE %text% O e.key IN (SELECT ... FROM tags)
Drift Muestra aleatorio, sesgado a no visitados

Paso 3: Reordenar según intent

Intent Orden
Explore r.ord ASC (estructural)
Review e.reviewDue ASC (más urgente primero)
Seek Relevancia (TF-IDF básico o coincide)
Drift Random()

✅ DISEÑO: Estabilidad espacial para Parcour como vista dinámica

1. Anclaje espacial: lo que nunca cambia

Regla de hierro: Cada Locus tiene una posición base determinada por SON.ord.

Propiedad Valor fijo
Eje Z (profundidad) z_base = ordIndex * slotSpacing
Lateralidad base side = ordIndex % 2 (0 = izquierda, 1 = derecha)
Altura base y_base = eyeLevel (constante para todos)
Orientación base Mirando al centro del pasillo

Por qué: La memoria espacial humana se ancla en posiciones absolutas relativas. Si ord=3 siempre está a la misma profundidad, el usuario desarrolla un mapa mental aunque los loci cambien de aspecto o relevancia.

---

2. Límites de transformación por intención

Cada intención puede desplazar los loci dentro de un radio de tolerancia desde su posición base.

Intención Desplazamiento Z Desplazamiento X Rotación Escala Visibilidad
Explore 0 (exacta) 0 (exacta) 0 1.0 100%
Review ±0.5 slots ±0.2 m -5° a +5° 0.9–1.1 Los reviewDue más brillantes
Seek Solo relevantes visibles Centrados 0 1.0 Solo matches
Drift ±1.0 slot ±0.5 m ±15° 0.8–1.2 Aleatorio con peso

Regla de tolerancia: Ningún Locus puede desplazarse más de 1.5 slots de su z_base. Esto asegura que ord=3 nunca aparezca antes que ord=2 en el eje Z.

---

3. Transiciones entre intenciones

Regla de continuidad: Al cambiar de intención, los loci no desaparecen ni saltan. Se mueven con lerp desde su posición anterior a la nueva.

Fase Duración Comportamiento
Inicio 0 ms Capturar posiciones actuales
Cálculo 1 frame Calcular destinos según nueva intención
Movimiento 300–500 ms lerp posición, rotación, escala
Estabilización 100 ms Ajuste final + snap si muy cerca

Regla de visibilidad: Ningún Locus debe estar invisible durante la transición (excepto Seek, que puede ocultar no relevantes al final).

---

4. Señales visuales mínimas para orientación

El espacio debe comunicar dónde estás y qué cambió sin UI textual.

Señal Propósito Implementación
Sombra base Recordar posición original Cada Locus proyecta una sombra tenue en su z_base, incluso si se movió
Estela de movimiento Mostrar dirección del cambio Partículas o rastro tenue durante transición (se desvanece)
Luz de intención Indicar modo actual Color de luz ambiental cambia sutilmente (frío = explore, cálido = review, neutro = seek)
Marcadores de profundidad Referencias espaciales Elementos fijos en techo/piso en intervalos regulares (ej: cada 5 slots)
Degradado de suelo Sentido de avance Textura que se repite o líneas que convergen al fondo

5. Reglas de reordenamiento perceptible vs memoria espacial

El dilema: Si los loci se mueven demasiado, el usuario pierde el mapa mental. Si no se mueven nada, la intención no se siente.

Solución híbrida:

Tipo de cambio Perceptible Afecta memoria Regla
Brillo/color Sí No Libre
Escala Sí Leve ±20% máximo
Rotación Sí Moderado ±15° máximo
Desplazamiento Z Sí Alto Limitado a 1.5 slots
Desplazamiento X Sí Bajo Limitado a 0.5 m
Ocultar Total Alto Solo en Seek, con fade

Regla de compensación: Si un Locus se mueve mucho (>1 slot), debe mantener su sombra base visible para recordar su lugar original.

**CONTRATO — REALM LOADING & WARP GRAPH (ALEXANDRIA 14.06+)**

Ubicación sugerida en ORM:
`5.x Realm & Loading Contract`

---

**Realm Active Contract**

Un único realm puede estar activo en runtime.

El realm activo define el conjunto de datos que debe existir en SQLite para renderización.

El realm activo incluye:

* su parcour
* sus loci (rooms)
* sus object slots
* sus seeds persistentes
* sus warps habilitados

Godot nunca decide el realm activo.

RAZ12 es responsable de seleccionar y cambiar el realm activo.

---

**Materialization Contract**

RAZ12 debe materializar en SQLite el estado completo navegable del realm activo.

Esto implica:

* todas las rows necesarias en `entries`
* continuidad estructural por `parentKey + seq`
* ausencia de huecos estructurales
* seeds persistentes ocupando todos los slots

Godot no crea, no completa y no corrige estructura.

Godot solo lee lo materializado.

---

**Warp Graph Contract**

Warp es una relación transversal KEY↔KEY.

Warp no altera:

* `parentKey`
* `seq`
* jerarquía

Warp define conectividad entre realms o dentro de un mismo realm.

Si un warp está habilitado, su destino debe ser resoluble en runtime.

---

**Warp Loading Rule**

RAZ12 debe garantizar que todo destino de warp habilitado esté disponible para render.

Esto puede cumplirse de dos formas:

1. El target ya existe en el realm activo materializado
2. El target es materializado adicionalmente como nodo accesible

Godot no resuelve warps faltantes.

Si un warp apunta a un KEY no materializado, es error de Builder.

---

**Runtime Scope Contract**

SQLite runtime contiene:

* el realm activo
* los nodos necesarios para navegación inmediata (incluyendo warps)

SQLite no requiere contener todos los realms del sistema.

La library completa es responsabilidad de RAZ12, no de Godot.

---

**Bridge Contract for Realm Switch**

Cambio de realm o navegación por warp:

1. RAZ12 decide destino
2. RAZ12 materializa estructura necesaria en SQLite
3. RAZ12 emite señal de bridge (`refresh_now`)
4. Godot recarga y renderiza nuevo contexto

Godot no inicia cambio de realm por sí mismo.

---

**Godot Responsibility (en este contexto)**

Godot:

* lee SQLite
* renderiza parcour, rooms y slots
* renderiza targets de warp si existen
* emite eventos de navegación (`open_key`, etc.)

Godot no:

* crea rows
* resuelve warps
* cambia realm activo
* completa estructura

---

**RAZ12 Responsibility (en este contexto)**

RAZ12:

* gestiona library de realms
* selecciona realm activo
* materializa estructura completa
* asegura integridad de slots (`parentKey + seq`)
* asegura disponibilidad de destinos de warp
* gestiona lifecycle (`seed ↔ active`)
* emite señales de bridge

---

**Invariant Rule**

En todo momento:

Todo KEY accesible en Godot debe existir en SQLite.

Si no existe, es error de materialización en RAZ12.

---

**Resumen operativo**

RAZ12 construye el grafo navegable.
SQLite lo contiene.
Godot lo renderiza.
Warp define conectividad.
